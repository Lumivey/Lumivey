Date: 2026-09-19. INTERNAL / CORE. Scope: `LUMIVEY_DB` project `odd-term-62838732`, **non-default** Neon branch `br-green-lake-b2xh1tni`, `neondb`; draft PR #49 only. No Neon DDL or data mutation was executed in this checkpoint; only read-only catalog queries and draft-branch GitHub changes. Do not publish implementation details.

## Verified on the actual Preview database

- `Neon.get_branch`: target is ready, `primary=false`, `default=false`.
- `pg_authid`: `lumivey_discovery_app_preview` is `LOGIN=true` but has no stored password, no BYPASSRLS/superuser, no Discovery API schema USAGE. Function owner `lumivey_discovery_function_owner` is NOLOGIN and has no password. **PostgreSQL `CONNECTION LIMIT 0` means unlimited connections, not login disabled.** Earlier checkpoints that interpreted it as a login prohibition were mistaken; absent password and lack of schema/function grants are the real blockers. This role has no functional Preview application credential.
- `pg_get_functiondef`, `pg_proc` and ACL audit: two functions exist (`rotate_guest_resume`, `record_guest_correction`), both restricted NOLOGIN owner, SECURITY DEFINER, fixed search_path, app EXECUTE=false, PUBLIC EXECUTE=false. The function owner's scoped RLS policies exist on dossiers/events; assets have no policies. No independent limited-role database connection was used.
- **Discovered real audit gap:** `has_table_privilege('lumivey_discovery_function_owner', dossier, 'SELECT')` is false but `has_any_column_privilege(..., 'SELECT')` true; likewise UPDATE false at table level but true at column level. The previous preflight only checked table-wide rights; it could erroneously allow the application after receiving a direct column grant.
- Updated `lib/lumivey/guest-dossier-db-preflight.ts` to inspect `has_any_column_privilege` for SELECT/INSERT/UPDATE/REFERENCES, plus table DELETE/TRUNCATE/TRIGGER, rejecting every unexpected permission. Updated regression tests and verified GitHub Actions `v0 build safety` run **35434165231** passed; emergency paid-route shutdown run **35434165270** passed. Node tests use mocks; passing them does not imply Neon A/B proof.
- Independently queried all **three actual Neon Preview Discovery tables** with `has_any_column_privilege` for application role. Each has RLS enabled+forced, all SELECT/INSERT/UPDATE/REFERENCES column checks false, all DELETE/TRUNCATE/TRIGGER false. No rights were granted or released.

## Remaining real gate, NOT passed

The Neon SQL connector runs as privileged `neondb_owner` and does not provide distinct authenticated DB sessions as the application role. A SQL `SET ROLE` or temporary administrator function EXECUTE grant cannot substitute for two independent, limited login connections. Do not reset/print credentials into GitHub, chat, tests or logs; do not use owner URL in Vercel. Arrange approved secret handoff directly into Preview-only runtime/CI secret storage, then run two genuinely separate sessions through the limited role, validating A/B swaps, old/reused/expired/claimed digest, concurrency, version CAS, rollback and per-dossier replay. After the proof, audit privileges and ensure no temporary grants, roles or synthetic customer records remain. Only then review controlled `GRANT USAGE` + function-specific EXECUTE to application and a server-only authenticated chat adapter. No claims of complete isolation, no production changes or paid API activation.
